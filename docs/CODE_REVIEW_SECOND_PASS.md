## New findings

### 7. [P2] Coarse corridor cells can create invalid weather coordinates

Location: `backend/routing/geometry.py:78–85`, particularly the unchecked cell-center calculation at line 84.

The normal corridor builder filters center coordinates to supported bounds. When more than 64 cells are needed, it switches to `coarse_corridor()`, which applies no equivalent bounds check. A cell containing an in-bounds route point can have its center beyond longitude 180°. Those centers are passed to the weather API along with valid checkpoint coordinates.

Reproduction uses explicitly synthetic route geometry, not a claimed real road itinerary:

1. Build a 201-vertex path at latitude 61°, with longitude increasing from 154.99° to 179.99°. It never crosses the antimeridian, stays inside the application's accepted coordinate bounds, and has approximately 837 miles of annotated distance—below the 1,600-mile limit.
2. `corridor_cells()` selects its coarse fallback and returns 25 cells. One cell center is `[180.09862365468305, 60.839467453290546]`.
3. Through `build_plan()` with 10-mile spacing, the weather request contains longitude **180.099** after normal coordinate rounding.
4. In an integration reproduction where all valid locations have a complete Low forecast and the provider mock rejects out-of-bounds coordinates, the invalid location causes its whole weather batch to fail. Result: **47.4 unknown route miles, incomplete route, and no recommendation**.

The invalid request is generated by the application, so this should not be presented as unavoidable provider unavailability. Actual live provider access is blocked; the downstream rejection was simulated according to the provider's coordinate contract.

Suggested fix: constrain/rebuild the coarse cells within supported bounds, deriving each representative location from the resulting valid cell. Ensure every center sent upstream is valid without silently dropping corridor coverage. Add regressions for eastern/western longitude boundaries, high latitudes, and the >64-cell fallback, plus a planning test that would fail if an invalid generated coordinate poisons a valid checkpoint batch.

### 8. [P2] Endpoint markers hide checkpoint risk colors and intercept their popups

Location: `frontend/src/TripMap.tsx:87–88`; affected checkpoint pane at lines 75–85.

Checkpoint markers are rendered at z-index 460 with radii 5–7px. The larger origin/destination markers render at z-index 470 with radius 9px, at the same coordinates in the demo and whenever routing does not snap them elsewhere. Endpoint markers have permanent place-name tooltips but no weather popup. They therefore cover the weather markers, including their risk colors, and consume clicks meant for the first/last checkpoint.

Reproduced with actual Chromium pointer clicks on the demo map, on both desktop and mobile viewports:

| Target | Element receiving the click | Weather popup count |
|---|---|---:|
| Origin checkpoint | `leaflet-endpoints-pane` | 0 |
| Destination checkpoint | `leaflet-endpoints-pane` | 0 |
| Interior checkpoint | `leaflet-checkpoints-pane` | 1 |

The text checkpoint table still exposes endpoint measurements; the defect is in the map's risk presentation and interaction. Existing browser tests click only an interior checkpoint and do not detect it.

Suggested fix: combine endpoint identity and weather details in one marker/popup, or render a non-interactive endpoint decoration that allows checkpoint clicks through. Preserve access to endpoint weather when the selected route changes, and ensure any endpoint risk color agrees with the selected route's actual risk. Add first/last-checkpoint pointer tests on desktop and touch/mobile.
